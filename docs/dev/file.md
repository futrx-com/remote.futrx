# Global update lifecycle hooks for the 2FA service

## Objective

Introduce one application-wide observer publisher for update lifecycle events and make the 2FA service publish its durable mutation attempts through it. The concrete publisher must live at:

```text
backend/internal/integration/lifecycle/publishers/core.go
```

The change is intentionally small. It must not reorganize the existing auth package, move existing models or ports, change HTTP contracts, change 2FA policy, or add lifecycle behavior to unrelated services.

In this plan, the 2FA service is an event producer. Global observers subscribe to the shared publisher and receive events generated by 2FA mutations. The self-update service is not part of this change.

## Behavior that is frozen

The refactor must preserve all existing observable 2FA behavior:

- Enrollment begins without writing server-side state.
- Enrollment confirmation validates the signed token, authenticated email, and TOTP code before saving the record.
- TOTP challenges update `LastUsedTOTPCounter` and continue rejecting replayed counters.
- Recovery-code challenges consume exactly one recovery-code hash.
- Disabling 2FA still requires a valid TOTP or unused recovery code and deletes the record.
- Recovery-code regeneration still requires a current TOTP code and atomically replaces the stored hashes.
- Per-account locking continues to serialize every read-modify-write operation.
- Cache changes continue to happen only after the corresponding store operation succeeds.
- Existing errors, error wrapping, return values, side-effect counts, and HTTP mappings remain unchanged.
- The best-effort session and recovery-alert work in `security.go` retains its current ordering and failure policy.
- With no registered observers, request results and persistence behavior remain identical to the current implementation.

The existing focused baseline is green:

```text
go test ./internal/service/auth ./internal/transport/http/handlers ./internal/service
```

## Current design diagnosis

### Missing application-wide lifecycle owner

There is currently no shared update observer publisher. The nearest callback mechanism, `runhub.SetRunningSubscriber`, is specific to run state and is not appropriate for application-wide update events.

**Principle:** lifecycle dispatch needs one cohesive owner, and dependencies must be constructed explicitly at the composition root.

**Fix:** add the concrete, concurrency-safe publisher in `backend/internal/integration/lifecycle/publishers/core.go`, construct one instance during application startup, and inject its narrow publishing capability into auth.

### Repeated 2FA persistence boundaries

`backend/internal/service/auth/twofactor.go` performs durable state changes at the following boundaries:

- `ConfirmEnrollment`: store save and cache update around lines 154-158.
- `VerifyChallenge` with TOTP: store save and cache update around lines 184-188.
- `VerifyChallenge` with a recovery code: store save and cache update around lines 196-200.
- `Disable`: store delete and cache update around lines 220-224.
- `RegenerateRecoveryCodes`: store save and cache update around lines 248-252.

Adding callbacks separately to every return branch would duplicate lifecycle policy and make it easy to omit a failure or emit completion too early.

**Principle:** repeated lifecycle and ordering policy should have one semantic owner.

**Fix:** retain operation-specific core logic, but wrap each mutating entrypoint with a small common lifecycle runner that guarantees one started event and exactly one terminal event.

### Dependency direction risk

The 2FA service must not import the concrete `integration/lifecycle/publishers` package. That would leak an integration detail into application policy.

**Principle:** services depend on consumer-owned capabilities; the composition root supplies concrete integrations.

**Fix:** declare the smallest publishing capability in the existing `backend/internal/service/auth/ports.go`. The concrete publisher will satisfy it structurally, and `backend/cmd/remote/main.go` will wire the dependency.

## Target design

### Concrete global publisher

Create `backend/internal/integration/lifecycle/publishers/core.go` with these responsibilities:

- Define the generic `UpdateEvent` delivered to observers.
- Define the observer contract.
- Own the observer registry.
- Support subscription and unsubscription.
- Snapshot observers under a read lock and release the lock before callbacks.
- Invoke observers synchronously in registration order.
- Publish started, completed, and failed lifecycle states.

The intended public shape is:

```go
type UpdateEvent struct {
    Source    string
    Operation string
    Subject   string
}

type Observer interface {
    OnUpdateStarted(context.Context, UpdateEvent)
    OnUpdateCompleted(context.Context, UpdateEvent)
    OnUpdateFailed(context.Context, UpdateEvent, error)
}

type Core struct {
    // private synchronization and observer state
}

func New() *Core
func (c *Core) Subscribe(observer Observer) (unsubscribe func())
func (c *Core) PublishUpdateStarted(ctx context.Context, source, operation, subject string)
func (c *Core) PublishUpdateCompleted(ctx context.Context, source, operation, subject string)
func (c *Core) PublishUpdateFailed(ctx context.Context, source, operation, subject string, err error)
```

`Source`, `Operation`, and `Subject` are deliberately exact strings rather than an open metadata map. The first producer uses:

```text
source: two-factor
operations:
  confirm-enrollment
  verify-challenge
  disable
  regenerate-recovery-codes
subject: normalized account email
```

No TOTP secret, submitted code, enrollment token, plaintext recovery code, recovery-code hash, session token, or persisted record may be included in an event.

The requested method name is normalized to `OnUpdateFailed`; the misspelled `OnUpdateFaild` variant will not be introduced.

### Application-global, not package-global

`Core` is global in application scope: startup creates one instance and shares it with all producers and observers. There must be no mutable package-level default publisher, `init` registration, or hidden singleton.

This gives every service access to the same hook when explicitly wired, while preserving test isolation and making startup dependencies visible.

### Consumer-owned auth capability

Add this narrow dependency interface to `backend/internal/service/auth/ports.go`:

```go
type UpdateLifecyclePublisher interface {
    PublishUpdateStarted(ctx context.Context, source, operation, subject string)
    PublishUpdateCompleted(ctx context.Context, source, operation, subject string)
    PublishUpdateFailed(ctx context.Context, source, operation, subject string, err error)
}
```

Keep the 2FA source and operation names as private constants beside the 2FA implementation. They are implementation-only semantic identifiers, not runtime configuration.

### Dispatch semantics

Each durable 2FA mutation follows this sequence:

1. Normalize the account email and construct the non-sensitive lifecycle identity.
2. Publish `Started` once.
3. Execute the existing operation-specific validation, account locking, persistence, and cache update.
4. Release the per-account lock.
5. Publish `Completed` when the operation returned `nil`.
6. Otherwise publish `Failed` with the exact error that will be returned to the caller.
7. Return the original result and error unchanged.

Terminal callbacks run after the operation-specific core method returns. Observers may therefore query settled state without re-entering a held 2FA account lock.

Observer methods return no error. An observer cannot replace a successful 2FA result or mask the service's original failure. Observers are trusted in-process components and must not panic. The first implementation will not add asynchronous queues, panic recovery, retries, timeouts, or durable event delivery.

An invalid proof, invalid enrollment token, missing enrollment, replayed TOTP, random-number failure, store read failure, store write failure, or store delete failure is an attempted update and therefore produces `Started` followed by `Failed`.

The following operations publish no lifecycle event because they do not durably mutate 2FA state:

- `BeginEnrollment`
- `Enabled`
- `RecoveryCodesRemaining`
- `load`
- `setCache` when called only as an internal consequence of another operation

- Successful mutations update the store before the cache becomes observable.

### 2. Implement the global publisher


Tests must prove:

- Callbacks are invoked without holding the registry mutex; an observer may subscribe or unsubscribe from inside a callback without deadlock.

### 3. Introduce the auth publishing seam

Update:

```text
backend/internal/service/auth/ports.go
backend/internal/service/auth/service.go
backend/internal/service/auth/twofactor.go
```

Work in mechanically safe order:

1. Add `UpdateLifecyclePublisher` to `ports.go`.
2. Add it as an explicit auth construction dependency and reject `nil` with a precise constructor error.
3. Pass it into `newTwoFactorAuthenticator` and store it on that private component.
4. Extract the current bodies of the four mutating entrypoints into private core methods without changing their statements or ordering.
5. Make the existing entrypoints delegate through the common lifecycle runner.
6. Keep current method signatures and all callers unchanged apart from constructor dependency wiring.

The lifecycle runner must support operations with differing result shapes without using `any`, reflection, unsafe casts, or broad result bags. Prefer small typed wrappers around the private core methods; accept a small amount of repeated result plumbing rather than weakening types.

Do not publish from `security.go`. Publishing there would miss direct uses of `twoFactorAuthenticator`, conflate best-effort session/alert work with the core 2FA state change, and make completion semantics inconsistent.

### 4. Wire the single publisher at startup

Update the existing composition path:

```text
backend/cmd/remote/main.go
backend/internal/service/services.go
```

Steps:

1. Construct one `publishers.Core` in `main.go` before constructing the service set.
2. Add the narrow lifecycle publisher to `service.Dependencies`.
3. Forward it through `service.NewAuth` into `serviceauth.New`.
4. Update constructor-focused tests with lightweight recording or no-op publishers owned by those test packages.
5. Do not register a production observer until a concrete consumer and its required behavior are separately specified. The empty shared publisher preserves behavior while making the global hook available.

This step must not attach the self-update service or alter HTTP handler construction.

### 5. Verify 2FA lifecycle coverage

- Recovery-code challenge success, including one-code consumption.
- Invalid and replayed challenges.
- Disable success and failure.
- Recovery-code regeneration success and failure.
- Store failures return the identical original error and publish it through `Failed`.
- Event subjects contain normalized email addresses.
- No event includes secret or proof material.
- `BeginEnrollment` and read-only methods emit nothing.
- A completion callback may call `Enabled` or `RecoveryCodesRemaining` without deadlock and sees the settled state.

## Refactoring-skill validation checklist

### Scope and behavior

- The plan changes only global lifecycle publication, 2FA mutation wrapping, constructor wiring, and focused tests.
- Existing outputs, errors, storage behavior, lock behavior, cache behavior, and HTTP mappings are explicitly frozen.
- No discovered bug is fixed as part of the refactor.
- No unrelated auth, frontend, self-update, storage, or transport cleanup is included.

### Responsibility and dependency direction

- `integration/lifecycle/publishers/core.go` has one responsibility: in-process observer registration and dispatch.
- The publisher does not own 2FA policy or update policy.
- Auth depends on its own minimal publishing capability, not the concrete integration package.
- Dependency construction remains in `main.go` and the existing service composition path.
- No import-time startup or registration is introduced.

### Types and contracts

- The observer surface is small and cohesive.
- Lifecycle identity uses explicit fields rather than `map[string]any` or arbitrary metadata.
- Sensitive 2FA values are excluded by construction.
- Observer failures cannot replace application results because observer methods return no error.
- The requested concrete path is retained without moving existing public auth models or ports.

### Lifecycle correctness

- Every observed attempt has one `Started` event and one terminal event.
- `Completed` occurs only after durable storage and cache synchronization succeed.
- `Failed` carries the same error returned by the operation.
- Observer callbacks do not run under the publisher mutex or the 2FA per-account lock.
- Multiple observers have deterministic registration-order delivery.

### Verification and commits

- A characterization commit precedes the structural change only for uncovered behavior.
- Every implementation commit has a narrow verification command.
- Race testing covers the shared publisher and account-scoped mutation paths.
- Full Go tests and vetting close the work.
- Unrelated working-tree changes remain untouched.

## Deliberately not included

- Moving existing auth data definitions into new `model/` directories.
- Moving existing auth interfaces into new `port/` directories.
- A repository-wide lifecycle or event-system migration.
- Publishing self-update, project, chat, schedule, or user-setting events.
- Asynchronous delivery, persistence, replay, retries, timeouts, priorities, filtering, or wildcard subscriptions.
- A package-level global singleton.
- Production logging, metrics, notifications, or auditing observers.
- Frontend or HTTP API changes.
- Changes to the updater, deployment scripts, infrastructure, Caddy, LXD, or workspace images.

These exclusions keep the requested change reviewable and prevent the global hook from turning into an unbounded event-bus rewrite.

## Outcome

**Deviations from the plan:** None. `ConfirmEnrollment`'s lifecycle subject is `normalizeEmail(expectedEmail)` (the authenticated caller's account), computed before any validation runs — this was necessary rather than a choice, since the pending token (and its embedded `pending.Email`) isn't trustworthy until after verification, and the plan requires a `Started` event even for an invalid-token attempt.

**Plan defects:** None found. The plan's dispatch semantics, the four mutation boundaries, and the file layout all matched the current code exactly.

**Steps not fully verified:** None outstanding. Step 3 has no standalone verification command of its own in the plan (its command is folded into step 5's), so it is marked `verified-indirectly` against step 5's coverage and the full test/vet run rather than a dedicated command.

**Left behind:** No production observer is registered yet, exactly as the plan specifies ("Deliberately not included"). A future change wiring a concrete consumer (logging, auditing, etc.) is expected and out of scope here.

**For the next plan in this area:** `enrollTestAccount` in `twofactor_test.go` already performs one real `ConfirmEnrollment` (and thus one Save call and one cache-population of BeginEnrollment's "not enrolled" nil placeholder) as test setup — any future characterization or lifecycle test built on it needs to account for that baseline state/call count rather than assuming a virgin store or empty cache.
